# Iteration 19：WALとクラッシュリカバリ

## 永続性とバッファプール

Iteration 15のバッファプールは，書き換えたページを枠に残す．ファイルに書くのは，追い出すときかデータベースを閉じるときである．
プロセスが途中で止まると，枠に残っていた変更は失われる．コミットしたと返した変更が失われるので，ACIDの永続性(Durability)を満たさない．

コミットのたびに書き換えたページをすべてファイルに書けば失われないが，ページは表のあちこちにあり，ディスクの別々の場所への書き込みになる．1行の変更でも8192バイトのページを何枚も書く．

## WAL

WAL(Write-Ahead Logging，先書きログ)は，ページを書く代わりに，変更の記録(ログ)を1つのファイルの末尾に順に書く方法である．

- 末尾に続けて書くので，ディスクの離れた場所を書くより速い．
- コミットでは，そのトランザクションのログがディスクに届くまで待つ．ページはまだファイルになくてよい．
- プロセスが止まったら，次に開くときにログを読んで，ページに変更をやり直す(REDO)．

WALが守る規則は2つである．

1. コミットを返す前に，そのトランザクションのコミットのレコードまでを，ディスクに届ける．
2. ページをファイルへ書く前に，そのページの変更のレコードを，ディスクに届ける．

2つ目の規則のため，ページごとに，最後の変更のレコードのログの中の位置(LSN，Log Sequence Number)を覚えておく．ページを書き戻す前に，ログをそのLSNまでディスクに届ける．
PostgreSQLはページの先頭に`pd_lsn`としてLSNを書く．`ferrodb`は，バッファプールの枠に`page_lsn`として持つ．

## 何を記録するか

`ferrodb`のログは，ページを書き換えたあとの内容を丸ごと記録する(物理ログ，ページイメージ)．

- 同じレコードを何度やり直しても，ページは同じ内容になる(冪等)．どのレコードまでページに反映済みかを知らなくても，最後のチェックポイントのあとを順にやり直せばよい．
- 1つのタプルの変更でも8192バイトを記録するので，ログは大きくなる．

PostgreSQLは，「このページのこのスロットにこのタプルを置いた」のような変更の内容を記録する．ログは小さいが，やり直すときは，ページの`pd_lsn`とレコードのLSNを比べて，反映済みのレコードを飛ばす．
チェックポイントのあとに初めてページを書き換えるときだけは，PostgreSQLもページを丸ごと記録する(full page writes)．書きかけで壊れたページを，丸ごとの記録から戻すためである．

## トランザクションの記録

ログには，ページの変更のほかに，トランザクションの開始，コミット，中止を記録する．

- やり直すときは，コミットのレコードがあるトランザクションをコミット済みに，ないトランザクションを中止にする．
- 中止したトランザクションが書き換えたページも，そのままやり直す．MVCCでは，中止したトランザクションの版は見えないので，変更を取り消す(UNDO)必要がない．PostgreSQLも，リカバリでUNDOをしない．

## チェックポイント

ログを最初からやり直すと，ログが長いほど開くのに時間がかかる．
チェックポイントは，ある時点までの変更をすべてファイルに書き終えたことをログに記録する．

1. 変更されたページをすべてファイルに書き，ディスクに届ける．
2. トランザクションの状態をファイル(`xact`)に書く．
3. チェックポイントのレコードを書き，ディスクに届ける．

やり直すときは，最後のチェックポイントのレコードのあとだけを読めばよい．
`ferrodb`の`CHECKPOINT`文は，チェックポイントを取る．データベースを開くときと，表とインデックスを作る文と消す文のあとにも取る．表を消してから同じ名前の表を作ったとき，消した表のページの記録をやり直さないためである．

PostgreSQLは，チェックポイントより前のログのファイルを消すか，使い回す．`ferrodb`のログのファイルは，末尾に書き足し続ける．

## 壊れたログの末尾

レコードを書いている途中でプロセスが止まると，ログの末尾に書きかけのレコードが残る．
レコードごとにバイト数とCRC-32を書いておき，読むときに，バイトが足りないかCRC-32が合わないレコードで止まる．そこから後ろは，コミットを返す前に書き終えていない部分なので，捨ててよい．
