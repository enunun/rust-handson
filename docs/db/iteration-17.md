# Iteration 17：インデックスの利用

## インデックスを作る

`CREATE INDEX 名前 ON 表 (列)`は，表の列の値から行の位置を引くインデックスを作る．
`CREATE INDEX`は標準SQLにない拡張だが，多くのデータベースが同じ形の文を持つ．

- 作るときに，表の今の行をすべてインデックスに入れる．
- そのあとは，`INSERT`，`UPDATE`，`DELETE`で表の行を変えるたびに，インデックスの項目も加え，消す．
- `DROP INDEX 名前`でインデックスを消す．表の行は変わらない．

インデックスは，表とは別の構造である．同じ内容を2か所に持つので，行を変える文は，インデックスの数だけ仕事が増える．
読む速さと書く速さのどちらを重んじるかで，インデックスを作る列を選ぶ．

## 一意性制約とインデックス

Iteration 8では，`INSERT`のたびに表のすべての行を読んで，値が重ならないかを調べた．表の行が多いほど遅くなる．
一意性制約の列にインデックスがあれば，新しい値をインデックスで引くだけで，同じ値の行があるかがわかる．

- `ferrodb`は，`PRIMARY KEY`と`UNIQUE`の列に，制約と同じ名前(`EMP_PKEY`など)のインデックスを自動で作る．
- 制約のためのインデックスは，`DROP INDEX`で消せない．PostgreSQLも同じ形のエラー(`2BP01`)を返す．
- PostgreSQLも，一意性制約を一意なインデックスで実現する．

`UPDATE t SET id = id + 1`では，書き換えの途中で`2`が2つになる瞬間がある．
`ferrodb`は，書き換えたあとの値をインデックスで引き，見つかった行が今の文で書き換える行なら，違反としない．文が終わったときに一意であればよい，という規則を保つ．

## `NULL`とインデックス

`ferrodb`は，`NULL`をインデックスに入れない．

- 比較の条件(`=`，`<`など)は，`NULL`に対して真にならない．インデックスで範囲を引くとき，`NULL`の行は要らない．
- 一意性制約は，`NULL`どうしを重なりとみなさない．`NULL`を入れなければ，検査で気にしなくてよい．

PostgreSQLは`NULL`もインデックスに入れ，`WHERE col IS NULL`や`ORDER BY`にもインデックスを使える．

## インデックススキャン

インデックスで条件に合う行の位置を引き，その位置の行だけを読む読み方を，インデックススキャンと呼ぶ．

- `WHERE salary >= 450`なら，インデックスでキーが450以上の項目を順にたどり，その`RowId`のページとスロットを読む．
- 返す行は，キーの順に並ぶ．全件走査(ページとスロットの順)とは順序が違う．`ORDER BY`がなければ，行の順序は決まっていない．

### インデックスで決める条件と，残りの条件

`WHERE salary >= 450 AND dept = 'ops'`で，`salary`にだけインデックスがあるとする．

- `salary >= 450`は，インデックスで引くキーの範囲を決める条件である．インデックスで引いた行は，この条件を必ず満たす．
- `dept = 'ops'`は，引いた行を1つずつ調べる残りの条件である．`IndexScan`の上の`Filter`に置く．

`salary > 400 AND salary <= 500`のように同じ列の条件がいくつあっても，範囲を狭めて1回のスキャンにできる．
`OR`でつないだ条件や，`salary + 1 > 450`のように列を式にした条件は，キーの範囲にできない．

PostgreSQLの`EXPLAIN`は，前者を`Index Cond`，後者を`Filter`として分けて表示する．

## 全件走査との選択

インデックススキャンが速いとは限らない．

- インデックススキャンは，行ごとに別のページを読みうる(ランダムアクセス)．条件に合う行が表の大部分なら，ページを順に読む全件走査の方が速い．
- 条件に合う行の割合を選択率と呼ぶ．選択率の小さい条件ほど，インデックスで読む行を減らせる．

PostgreSQLのプランナーは，表の統計情報(値の分布)から選択率を見積もり，読み方ごとの費用を比べて選ぶ(コストベースの最適化)．
`ferrodb`のプランナーは，使えるインデックスがあれば必ず使い，`=`の条件のあるインデックスを優先する，という規則で選ぶ(ルールベース)．
