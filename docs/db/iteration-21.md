# Iteration 21：同時接続，ラッチとロック

## 接続とセッション

データベースのサーバーは，多くのクライアントから同時に接続を受ける．接続ごとに，トランザクションの状態などを持つセッションがある．

- PostgreSQLは，接続ごとにプロセス(バックエンド)を作る．ページを置く共有バッファやトランザクションの状態は，すべてのプロセスで共有するメモリーに置く．
- `ferrodb`は，接続ごとにスレッドを作る．表とインデックス，トランザクションの状態，ログは`Database`にまとめ，すべてのスレッドが共有する．セッションの状態は，接続ごとの`Session`が持つ．

接続が途中で切れると，そのセッションのトランザクションは終わらないまま残る．進行中のままのトランザクションが作った版は，ほかのセッションからずっと見えない．
サーバーは，接続が切れたらそのトランザクションを中止する．`ferrodb`では，`Session`を捨てるときに中止する．

## ラッチとロック

共有するデータを複数のスレッドが同時に書き換えると，データ構造が壊れる．データベースは，目的の違う2種類の排他を使い分ける．

| | ラッチ(latch) | ロック(lock) |
| --- | --- | --- |
| 守るもの | メモリー上のデータ構造(ページ，バッファプールの表，ログの末尾) | データベースの内容(行，表) |
| 持つ期間 | 操作の間だけ(数マイクロ秒〜数ミリ秒) | トランザクションの終わりまで |
| 持つ主体 | スレッドやプロセス | トランザクション |
| デッドロック | 取る順序を決めて起こさない | 起こりうるので，見つけて片方を中止する |
| PostgreSQLの例 | 軽量ロック(LWLock)，バッファのピンと内容のロック | 行ロック，表ロック(`LOCK TABLE`) |

ラッチは，ページの途中まで書き換えた状態をほかのスレッドに見せないためのもので，トランザクションの意味(何が見えるか)には関わらない．
ロックは，トランザクションが読み書きした行を，ほかのトランザクションに書き換えさせないためのもので，分離レベルを実現する方法の1つである．

## `ferrodb`のラッチ

`ferrodb`は，次のラッチを持つ．

| ラッチ | 種類 | 持つ間 |
| --- | --- | --- |
| 表とインデックスとカタログ(`Storage`) | 読み書きラッチ | 1つの文を実行する間．問い合わせは読み取り，ほかの文は書き込み |
| トランザクションの状態 | 読み書きラッチ | 文を実行する間は読み取り．開始とコミットと中止の間は書き込み |
| ページ | 読み書きラッチ | ページを読むか書く間 |
| バッファプールの枠の割り当て | 排他ラッチ | ページをピン留めするか追い出す間 |
| ログ | 排他ラッチ | レコードを書く間と，ディスクに届くまで待つ間 |

- 問い合わせどうしは同時に動く．表を変える文は1つずつ動き，その間はほかの文を待たせる．
- ラッチは，取る順序(表とインデックス，トランザクションの状態，ログ)を決めているので，デッドロックしない．
- PostgreSQLは，表全体のラッチを持たず，ページのラッチと行のロックで，別の行を変える文も同時に動かす．

## 読み取りがブロックされない理由

ロックだけで分離するデータベースでは，トランザクションが行を書き換えると，その行を読みたいほかのトランザクションは，書き換えたトランザクションが終わるまで待つ．
MVCC(Iteration 18)では，書き換えは新しい版を作り，古い版を残す．読むトランザクションはスナップショットから見える版を読むので，書いているトランザクションの終わりを待たない．

```text
セッションA: START TRANSACTION
セッションA: INSERT INTO t VALUES (3)      -- xmin が A の版を加える
セッションB: SELECT COUNT(*) FROM t         -- A は進行中なので，その版は見えない．待たずに 2 を返す
セッションA: COMMIT
セッションB: SELECT COUNT(*) FROM t         -- 新しいスナップショットでは A はコミット済み．3 を返す
```

Bの`SELECT`が待つのは，Aの文が実行されている間(ラッチを持つ間)だけで，Aのトランザクションが終わるまでではない．
「読む側は書く側を待たせず，書く側は読む側を待たせない」ことが，MVCCを使う大きな理由である．

## 書く側どうし

2つのトランザクションが同じ行を書き換えると，MVCCでも調整が要る．
Aが行を書き換えて`xmax`に自分の番号を書く．Aのコミットの前に，Bも同じ行を書き換えると，Bの`xmax`でAの`xmax`は上書きされる．両方のコミットのあとは，AとBのそれぞれ加えた新しい版の両方が見え，1行だった行は2行になる．どちらの版も，相手の変更を含まない(更新の消失，lost update)．
PostgreSQLは，行を書き換える前に，その行を変えている進行中のトランザクションがあれば，その終わりを待つ．Iteration 22で，この待ち合わせと分離レベルを扱う．
